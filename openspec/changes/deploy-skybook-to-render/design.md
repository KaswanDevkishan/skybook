## Context

SkyBook currently runs as a single Django process with SQLite and development-oriented
settings. Exercise 11 introduces a hosted production environment without changing the
domain schema or public application behavior. Render will build the GitHub `main`
branch, run the WSGI application as a web service, attach managed PostgreSQL, and route
HTTPS traffic through its proxy. The design must keep local setup lightweight, keep
secrets outside Git, preserve all existing migrations and the database-enforced
duplicate-seat invariant, and remain understandable for a course project.

## Goals / Non-Goals

**Goals:**

- Provide a reproducible Render Web Service deployment driven by checked-in
  configuration and the locked `uv` dependency graph.
- Use Gunicorn for production WSGI serving, Render PostgreSQL for persistent data, and
  WhiteNoise for collected static assets.
- Separate local defaults from production enforcement through explicit environment
  configuration.
- Make deployment, migration, verification, troubleshooting, and rollback procedures
  clear and testable.
- Preserve SQLite development, current routes including `/health/`, current migrations,
  and all reservation invariants.

**Non-Goals:**

- Docker, Redis, Celery, background workers, uploaded-media features, or another web
  framework.
- Authentication screens, payments, checkout, external airline APIs, seat-map work, or
  unrelated interface changes.
- Schema changes or replacement of existing migrations.
- Durable app-local media storage; future uploads require object storage.

## Decisions

### Use one settings module with explicit environment parsing

The existing settings module will use small, strict helpers for booleans and
comma-separated lists. `DEBUG` will be read from the environment and default to false.
`ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` will accept comma-separated environment
values while retaining localhost development defaults outside Render. On Render,
configuration will fail unless either `RENDER_EXTERNAL_HOSTNAME` or a non-empty
`ALLOWED_HOSTS` is available; trusted origins likewise must resolve to a non-empty
Render HTTPS origin or explicit value.

Render's `RENDER` environment marker will distinguish the hosted production context.
In that context, a missing `SECRET_KEY` will fail fast instead of falling back to a
checked-in value. A clearly insecure local-only fallback may remain for management
commands and development outside Render. This makes the production contract
enforceable without requiring every local command to export secrets.

Alternative considered: split `settings.py` into development and production modules.
That adds import-path and documentation overhead without enough benefit for this small
project.

### Select PostgreSQL only when `DATABASE_URL` is present

Use `dj-database-url` to parse `DATABASE_URL`, with connection health checks and a
finite connection age suitable for a hosted web process. If the variable is absent,
retain the existing SQLite database definition unchanged. Use Psycopg 3's binary
distribution as the Python 3.12-compatible PostgreSQL driver.

Alternative considered: manually decompose PostgreSQL environment variables. Render
provides a database URL directly, so manual parsing would add error-prone configuration.

### Gate production HTTPS and static behavior on the Render environment

WhiteNoise middleware will sit immediately after Django's
`SecurityMiddleware`. `STATIC_URL` and `STATIC_ROOT` will always be defined. On Render,
the `staticfiles` storage alias will use WhiteNoise's compressed manifest backend;
outside Render it will retain Django's convenient non-manifest development storage.

Production will trust Render's `X-Forwarded-Proto` value through
`SECURE_PROXY_SSL_HEADER`, redirect HTTP to HTTPS, and enable secure session and CSRF
cookies. Hosts and trusted origins remain explicit inputs; neither wildcard hosts nor
disabled CSRF checks will be used.

Alternative considered: serve static files from Django or Render's ephemeral disk.
WhiteNoise integrates with the WSGI process and hashed `collectstatic` output without a
separate service.

### Describe infrastructure with a Render Blueprint

Add `render.yaml` containing one free-plan Python web service connected to one managed
PostgreSQL database. It will define:

- a fully qualified Python 3.12 runtime version;
- one fail-fast `&&`-chained build command using `uv sync --frozen --no-dev`, followed
  by `python manage.py migrate` and `collectstatic --noinput`;
- a start command invoking `gunicorn skybook.wsgi:application` and binding
  `0.0.0.0:$PORT`;
- `/health/` as the health-check path;
- non-secret configuration values plus generated or dashboard-supplied secret values.

The database URL will come from Render's internal database connection, and the secret
key will be generated by Render or entered in the dashboard. No credential value will
be checked in. Render does not make pre-deploy commands or Shell access available to a
free web service, so migration runs during the build. A future paid service should
prefer moving migration to `preDeployCommand` as an explicit release step.

Alternative considered: dashboard-only configuration. A Blueprint makes build, start,
health, and database wiring reviewable and repeatable while leaving secret values out
of source control.

### Verify configuration at both unit and process boundaries

Focused tests will reload or execute settings under controlled environment values to
cover safe `DEBUG` defaults, required Render secrets, list parsing, SQLite fallback,
PostgreSQL selection, WhiteNoise middleware order, static storage, and HTTPS security
settings. Implementation verification will also run the complete test and Ruff suites,
normal Django checks, migration drift detection, production-style `check --deploy`,
`collectstatic`, a Gunicorn WSGI import/startup smoke test, and strict OpenSpec
validation.

## Risks / Trade-offs

- [A malformed environment value could silently select unsafe behavior] → Accept only
  documented boolean values and test defaults and production cases.
- [Manifest storage can fail when templates reference missing static assets] → Run
  `collectstatic --noinput` in tests/verification and fail the build on errors.
- [Build-time migrations can make a bad release harder to roll back] → Fail the build
  immediately on migration errors, review migrations before release, prefer forward
  fixes, and document the free plan's limited recovery options.
- [Free Render PostgreSQL expires after 30 days and is later deleted] → Document the
  lifetime clearly and require upgrade or data preservation before expiry.
- [Render's filesystem is ephemeral] → Store only rebuildable collected static assets
  locally and document object storage for any future uploaded media.
- [Psycopg binary wheels trade a larger package for simpler builds] → Accept the modest
  package cost to avoid system-level PostgreSQL build dependencies on Render.
- [Production-only branches can drift from development] → Cover them with settings
  tests and production-like verification in the documented workflow.

## Migration Plan

1. Add and lock production dependencies, then implement settings and tests locally.
2. Add the Blueprint and documentation; verify all local and production-style commands.
3. Commit and push the reviewed change to GitHub `main`.
4. Create or apply the Render Blueprint, confirm generated secrets and the database
   connection, and allow the fail-fast build migration and static collection to
   complete.
5. Verify `/health/`, static assets, application pages, logs, and migration state; then
   create a superuser through a temporary, uncommitted local connection to the Render
   PostgreSQL external URL only if administrative access is needed.
6. For rollback, redeploy the last known-good commit or Render deploy while keeping the
   PostgreSQL service intact. Treat database rollback separately: prefer a forward fix;
   restore a backup or reverse only a reviewed reversible migration when necessary.
